## Alternative architecture comparison (no invented measured cost)

1. **Existing Tecnotron-only operational notes and handoffs:** no new dependency, but cross-chat discoveries and blocked obligations lack the tested shared ready/claim graph; risk of repeatedly rebuilding or prematurely starting a second TaskCycle. Actual current operational queue costs have not been instrumented end-to-end.
2. **GitHub Issues/Projects for all operational obligations:** provider durability and human visibility; creates planning/operational authority confusion and duplicated granular issue mutations, lacks qualified ready field mapping and checkpoint consumer semantics for all work. **Not recommended** as the automatic destination for every discovered dependency.
3. **Beads native Git remote for *non-authoritative operational backlog* + existing Product SOT/receipt contracts:** best evidence-led candidate. Already verified native GitHub persistence, detached Actions readers, concurrent ref conflict, claim, deferred Web-origin handoff and reconciliation. Avoids a bespoke orchestrator/queue/snapshot publisher. Adds tool version, Git ref ownership, credentials, backup and precise source dedup/replay constraints.
4. **Always-on Dolt server:** qualifies simultaneous local SQL writes in hosted Actions, but requires a permanent host, auth, backup, availability and maintenance. Neither need nor net benefit established relative to native Git remote and bounded optimistic conflict recovery. **Do not default**.

## Smallest useful consumer adaptation (experimental shadow, no Product effects)

A single **existing Product Control checkpoint** can read a *non-authoritative operational index*, indexed by an exact durable Git source:

1. Observe exact Tecnotron Product SOT and original TaskCycle/ref/receipt, the current Control checkpoint and competent authority **outside Beads**.
2. Fetch only qualified Beads source/graph from a pinned GitHub native Dolt ref (`bd bootstrap` into an isolated runner, or authorized local binding). No new scheduler, process monitor or automatic chat wake.
3. For each discovered obligation, correlate a stable externally preserved `SOURCE_REF` and immutable Git carrier ID, inspect `discovered-from` / `blocks`, and render **candidate next independent work**, **blocked by original dependency**, or **UNKNOWN NEEDS EXTERNAL RECONCILIATION**. These are operational observations, **not Product states**.
4. Product Control chooses whether an already authorized independent action can continue; Beads `ready` is not automatic admission. Optional native `--claim` is about duplicate consumer allocation, not Developer grant.
5. If a Beads write is required, derive/qualify one stable native ID from immutable origin, perform a single authorized bounded `bd` update/push, reconcile exact remote ref and original receipt; on collision do independent origin readback. No blind retry and no separate duplicate state store.
6. Never change current TaskCycle identity, reinitialize a blocked TaskCycle or run new Product lifecycle merely due to Beads issue status. Where Product was already authorized, use existing transition contract and expected Git/receipt gates.

This is **consumer adaptation**, not overlaying an unnecessary new Product gate. It can replace discovery/claim/inbox mechanics if needed while removing any corresponding bespoke queue/projection rather than maintaining both permanently. Avoid designing a general adapter until a real identified caller needs this projection.

## Qualification questions and explicit negative cases before deciding on physical changes

- **Source-only shadow control test:** use one exact *real historical or currently selected* Product subject read-only; never touch its active TaskCycle. Verify authority/gate and evidence from Product SOT, with Beads synthetic operational pointers kept in lab. Expected output is only a human-readable checkpoint work-choice projection.
- **Interruption:** A's Product operation remains unresolved; Beads records B discovered; B independent and separately authorized; after B completion, A resumes **same exact TaskCycle identity**, no lost obligations, no double starts.
- **Parallel write:** concurrent processors claim different operational issues; both track exact source and avoid cross-writing Product files; a Beads Git ref collision triggers readback/controlled later sync, not automatic Product retry.
- **Duplicate semantic source:** two writers with same origin must map to stable native ID and readback; `SOURCE_REF` / `--external-ref` alone proven insufficient.
- **Unknown:** Beads publication `UNKNOWN`, exact original execution attempt and pending Product effect must be reconciled separately; no incorrect `ready` admission or forced close.
- **Post-close discovery:** evidence finding after close enters Beads candidate index, but does **not** automatically open Product backlog, accept a candidate or transition GitHub Projects.
- **Portability/security:** verify GitHub remote ref ownership and backups, git token least privilege and windows path binding; local vs Actions interchangeable only for qualified profiles and evidence.
- **Component retirement:** before any deletion of current code, determine whether a named active consumer remains and capture current negative/full conformance under exact tree; tests alone not universal usage proof.
