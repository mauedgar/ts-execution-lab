## 3. Important native limits: do not conflate the three histories

1. **Dolt versioned issue/history**: can be shared by explicit remote sync and used as a durable operational state/history owner, subject to identity and multi-writer sync qualification.
2. **Beads events journal**: opt-in, local per replica/branch, sequence is clone-local, `bd dolt push/pull`/merge do not add journal entries; `bd_events_journal` and `bd_events_seq` live in `dolt_ignore`, are *not* versioned/pushed/federated. Retention floors are not consumer watermarks and can truncate slower consumers. A mirror must identify its replica and rebaseline after a sync/clone/change. This follows pinned [Beads v1.3.1 journal documentation](https://github.com/gastownhall/beads/blob/v1.3.1/docs/reference/events-journal.md); actual remote journal non-replication is **source-qualified**, not a cross-machine native test in 016.
3. **Tecnotron `RunEvent v2` / `RunState v2`**: typed, validated Product-specific run ID, event ID, sequences, actors, model routing and `DONE` requires `PENDING_ACCEPTANCE` / `developer` / `DEVELOPER_DECISION`; RunStore persists per-run JSONL, run state JSON and optional SQLite projection. None of these semantics is implied by Beads `bd history`, `bd close` or `events`. An independent binding, if adopted, must explicitly validate and preserve required fields and authority.
