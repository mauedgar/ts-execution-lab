## Security review issues that MUST be dispositioned before admission

1. **Windows ACL**: DirectorySecurity owner-only access rule must be empirically tested on the actual user/Windows host, including exact inherited ACL, link/junction/reparse ancestors, read/write prohibition for another unprivileged principal, inherited privileges on `privileges.db` and secret file. Windows Administrators/SYSTEM can still recover/replace data despite ACL; cannot claim administrator-resistant custody.
2. **DPAPI scope**: CurrentUser encryption binds recovery to the Windows identity and its profile/key material. An unattended future service running under another SID cannot decrypt. Define a controlled service identity/secret migration and an off-host encrypted backup/recovery mechanism **before** claiming host independence. A cold backup of only the database will not restore the encrypted SQL credentials.
3. **Credential lifecycle**: PowerShell strings are immutable and may remain in process memory; DPAPI protects at rest but not memory, admin inspection, debugger, antivirus and backups. No secret in Git, logs, ChatGPT, Commander, or user-facing receipts. Avoid logging PowerShell transcripts and platform command tracing for the effect process.
4. **SQL root/anonymous users**: The script changes `root@localhost` offline but does **not** enumerate/prove absence of other passwordless root/anonymous accounts. It is an **offline bootstrap candidate**, never sufficient to expose SQL even on tailnet. Requires distinct localhost authentication/reader/writer grants and negative tests, testing all relevant accounts, before any Serve.
5. **No audit replay proof**: A local JSON grant with matching fields can be forged. Source Hash + grant file Hash are useful tamper fences but not cryptographic issuance, do not replace independent competent Control and durable original receipt. Require an independent non-replay assurance bound to attempt ID, principal and exact write-set before executing.
6. **Dolt privilege semantics**: Offline Dolt `sql` CLI can be superuser regardless of SQL reader grant. `privileges.db` presence is only file existence, not independent second-process persistence or server authentication. SQL GRANT ALL to writer must be bounded to only lab DB; root/admin and file ACL must be validated independently.
7. **Failure handling**: Any process timing out may have created a partial privilege store. The candidate intentionally does not kill or clean it, and local preparation failures can leave a directory that blocks reentry; these are outcomes, not automatic rerun permission. Verify stdout/stderr redirection doesn't expose secrets or deadlock under large responses.
8. **Binary/source and host identity**: exact installed Dolt `2.6.2` executable SHA256 `DF49F737CB80FC0F32B02220C701F476D378F322FA1BB51D696728FDAE825B91` and Beads `1.3.2` SHA256 `280517091DDA13CB195A39F991144771117B2BC26A4D472612F8FC9FD80F46E2`, notebook `DESKTOP-DJLBEQH`. Check that no original 047B data root, SQL process, TCP 3307/14337 listener or existing Serve/Funnel is present. Hostname-only proof is insufficient against a hostile local actor.
